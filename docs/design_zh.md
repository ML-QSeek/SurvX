# 第一部分：理念与约定

## 1.1 核心理念

SurvX 范式定义了**一个基础能力单元 + 两个核心实体角色**，所有系统能力、运行逻辑、演化机制均基于该体系搭建，实现业务、算法、模型、外部组件的统一标准化治理。

### 1.1.1 基础能力单元：Q

Q 是系统最小功能单元，无复杂内部结构，仅承载**单一特征、单一能力**的空白功能容器，是全系统能力的统一抽象标准。

Q 具备高度通用性，可承载原生程序、业务算法、AI 模型、固定参数配置，也可封装外部程序、第三方框架、外部应用。在 SurvX 范式体系中，原生代码、算法模型、外部组件处于同一层级，遵循同一套架构规则组织、调度、运行。

Q 分类：

- **轻量 Q**：简单数学表达式、条件判断
- **复合 Q**：批量筛选聚合多组数据，用于组装 Matter 分层逻辑视图
- **神经网络 Q**：输入一组实体 ID 的值，输出向量/标量结果

Q 支持版本绑定。新版本 Q 不会自动替换存量引用，需要人工显式升级，保证实例稳定性。

### 1.1.2 核心实体角色：Matter 与 Energy

系统所有运行行为、状态变更、迭代演化，均由 Matter 实体与 Energy 数据变动协同完成，无独立裸业务逻辑、无静态固化执行流。

- **Matter（实体载体）**：具备多维度特征、结构化内部结构、自主协作机制的复杂实体，可嵌套包含 Q 能力单元，也可嵌套子级 Matter，是系统所有状态、能力、约束的承载主体。
- **Energy（驱动源）**：代表系统数据变动的现实性，是所有行为的唯一触发源头。表现为时序数据、参数快照、状态变更序列，静态数据为 Energy 的沉积形态。

**核心规则：系统任何行为发起，必然由一次 Energy 数据变动触发，形成全局连锁反应。**

### 1.1.3 Matter 三个核心视角

同一 Matter 实体可从外部、内部、自指三个维度定义：

| 视角 | 概念 | 核心本质 |
|------|------|----------|
| 外部视角 | Entity（实体） | 对外表现为标准化输入输出实体，遵循 y=f(x) 映射规则，外部系统仅通过契约调用其能力，无需感知内部结构 |
| 内部视角 | Field（场域） | 具备独立状态、内在机能、作用域、行为约束的结构化场域，拥有完整的内部协作与运行机制 |
| 自指视角 | Ego（自演化体） | 在 Field 基础上新增自我驱动、自我迭代、自我优化能力，可基于目标自主调整内部结构与运行逻辑 |

核心逻辑：Ego 并非独立全新实体，而是 **Field + 自我驱动机制（附属 Matter）** 的叠加组合，自我驱动机制本身也遵循 Matter 架构规范。

### 1.1.4 Field 五层基础结构（S-C-R-O-F）

Field 是基础结构化实体，为 Matter 必备形态。五层结构不强制全部完备，但必须具备核心 Structure 结构层，区别于无结构的基础 Q 单元。

| 层级 | 缩写 | 英文名称 | 核心含义 |
|------|------|----------|----------|
| 结构层 | S | Structure | 定义 Matter 的组成模块、基础构件、嵌套关系，是实体存在的基础载体 |
| 能力层 | C | Capability | 定义内部模块的运作方式、组合规则、可复用协作机能，支撑实体核心能力输出 |
| 关系层 | R | Relation | 定义当前实体与外部 Matter、外部组件、Q 单元的关联、协作、依赖与被调用关系 |
| 约束层 | O | Ordinance | 定义实体所有运行阈值、行为边界、执行规则、权限约束、异常拦截机制，是系统秩序的核心保障 |
| 特征层 | F | Feature | 定义实体整体核心特征，包含可注册机能、链路关联、性能指标、时效规则等非功能特征 |

### 1.1.5 Ego 七层演化结构（S-C-R-O-F-G-L）

Ego 基于 Field 五层结构拓展而来，新增**目标层、表征层**，具备自主演化能力。其中目标层（G）为必备构件，表征层（L）为可选构件。

| 层级 | 缩写 | 英文名称 | 核心含义 |
|------|------|----------|----------|
| 目标层 | G | Goal | 承载多维度自主目标，为实体自我驱动、迭代优化、结构调整提供核心方向，是 Ego 演化的核心动力源 |
| 表征层 | L | Symbol | 承载实体自我认知记录，支持认知与客观实际存在偏差，服务于自我复盘与迭代修正 |

架构细节补充：Ego 自我驱动机制的 Relation 关系层具备特殊用途，专门用于存储实体自身认知数据，支撑自演化逻辑闭环。

Matter 的七层/五层属于**逻辑视图**，不是物理表。引擎基于底层三张基础数据表聚合组装出分层视图，底层存储不需要感知分层概念。

### 1.1.6 数据工程语义分类

架构层面将所有数据划分为三类，对应不同存储形态与运行逻辑：

- **参数数据**：描述性截面快照数据，包含权重系数、基础配置等静态参数，无时间序列属性。
- **约束数据**：运行阈值、边界条件、执行规则类截面快照数据，用于全域行为管控。
- **经历数据**：实体演变、运行执行的时序序列数据，包含运行日志、迭代记录、交互轨迹、历史行情等时序信息。

### 1.1.7 触发源头规则

系统初始驱动源头为**引擎内置基础 Q 单元**，由其产生初始 Energy 扰动。同时外部输入数据、历史沉积数据变更、人工干预操作，均可作为触发源，启动系统运行链路。

## 1.2 术语与约定

### 1.2.1 hoc / dbfs 约定

- **hoc**：临时脚本态。
- **dbfs**：正式持久态。

之后文中所有 `hoc` 和 `dbfs` 都按此约定简写，不再展开。

### 1.2.2 hoc（临时脚本态）

基于独立 Python 文件开发，所有 Matter 实体、Energy 结构通过 Python 字典声明描述，无数据库依赖，支持快速迭代、原型验证、小规模实例调试。

- Matter：顶层是一个大字典，所有子 matter 都以长 key 和 value 的格式，显式写在这个字典中。
- Energy：一个字典。

### 1.2.3 dbfs（正式持久态）

采用多介质分离存储架构，实现结构、功能、数据解耦：

- Matter 结构化定义：持久化至 SQLite。
- Q 功能逻辑：独立文件系统存储，与数据库元数据建立映射。
- Energy 时序数据、参数/阈值快照：存储至 DuckDB，支撑时序查询、状态回放、演化追溯。

Matter 在 dbfs 中是一张单独的 matter 表，按字段来存。

# 第二部分：存储与运行规则

## 2.1 仓库工程结构

仓库源码结构 ≠ 用户业务开发应用结构。基于本框架产出的业务应用，拥有独立的轻量化目录规范。

```
项目根/
├── survx/               # 引擎本体
│   └── survx_engine/    # 引擎核心
├── models/              # 开发目录
│   └── survx/           # 开发中的引擎（真实文件）
├── works/               # 工厂，承载迭代、灰度验证
│   ├── solutions/survx/ # 试运行中的引擎（真实文件）
│   ├── tools/
│   └── examples/
├── instances/           # 可运行实例
│   └── survx_studio/    # 开发者工具实例
└── docs/                # 设计文档
```

**说明**

- `models`：开发目录，按子项目立项，不分 `tools` / `examples`
- `works`：工厂层，分 `solutions` / `tools` / `examples`
- `instances`：可运行实例，按项目粘贴，不分 `tools` / `examples`
- `models/survx` 与 `works/survx` 是引擎的开发版与试运行版，内部用空文件占位，防止无穷嵌套
- `instances` 里没有 `survx`，实例运行时引用根目录的 `survx`
- 发布链路：`models → works → instances`；`models/survx → works/survx → 根目录 survx`

## 2.2 数据模型与存储

范式本身不绑定任何存储介质。本原型为统一落地标准，固定采用 **SQLite + DuckDB 双存储**，结构、功能、数据分离。

### 2.2.1 存储介质

**SQLite**

- `<app名>.db`：Matter 结构表，只放本体结构
- `_forge.db`：质量控制表 `_forge`，单独文件，事务型，与本体结构明确区分

**DuckDB**

- `_<app名>.duckdb`：Energy 所有表，含参数、约束、关系、时序、经历、注册与上层观测

**文件系统**

- `q/`：Q 功能逻辑，独立 `.py` 文件，与数据库元数据建立映射

**运行时内存**

- `_state`：当前 tick 窗口状态表，由引擎维护，不落库

### 2.2.2 数据分类

**截面快照数据**

- 参数、约束类数据
- 存于 DuckDB，按 `version` 多版本共存，取最大 version 为当前有效

**时序演变数据**

- 经历、序列类数据
- 存于 DuckDB，按 `_tick` 逐条追加，用于趋势分析、历史回溯

**结构数据**

- Matter 结构
- 存于 SQLite，按路径 key 平铺，新增版本行，不原地覆盖

### 2.2.3 表清单

**`<app名>.db`（SQLite）**

- `<app名>`：Matter 结构表

**`_forge.db`（SQLite）**

- `_forge`：操作记录表

**`_<app名>.duckdb`（DuckDB）**

- `_parameter` 参数表
- `_constraint` 约束表
- `_relation` 关系表
- `_sequence` 序列表
- `_experience` 经历表
- `_intent` 意图表
- `_feedback` 反馈表
- `_language` 语言表
- `_train` 训练数据表
- `_report` 报告总结表
- `_llm` AI 协作表
- `_register` 实例级注册表

### 2.2.4 底层存储模型

原型底层采用扁平双字典模型：`data_store`（主数据字典）+ `tag_index`（标签索引字典），无深层嵌套，所有节点平铺顶层，依靠字符串 Key 表达层级关系。

持久层用 SQLite / DuckDB 按表存储；运行时加载为扁平 KV 模型 `data_store` + `tag_index`，变更写回持久层。

- **节点 ID**：子节点自增数字 ID，分配后永久不回收；新增节点追加在末尾，避免连锁改动。
- **节点生命周期**：业务层不物理删除节点，通过 `active` 布尔标记控制启停。`active=True` 参与 tick 运算；`active=False` 节点休眠，数据保留。父节点休眠不会自动级联失效子节点。
- **查询模式**：默认仅返回 active 生效节点；`include_inactive=True` 可读取休眠节点，用于历史回溯。
- **版本机制**：参数、约束、关系记录携带自增 `version` 版本号；更新生成新版本，旧版本永久保留，读取默认取最大有效 version。

### 2.2.5 表结构

字段定义以 `syntax_zh.md` 为准，本文档不重复定义。

### 2.2.6 可替换性

生产阶段可根据业务需求替换为 MySQL、PostgreSQL、时序数据库等。范式架构完全兼容，核心逻辑无需改造。

## 2.3 引擎核心机制

引擎本身是标准化基础 Q 单元，无独立决策能力，核心职责为**执行调度、秩序维护**，不掌控系统核心逻辑与生命周期。系统全生命周期由约束层（O）统一管控，引擎仅为执行载体。

### 2.3.1 双引擎体系划分

| 引擎类型 | 驱动对象 | 核心特征 | 启动与运行逻辑 |
|----------|----------|----------|----------------|
| Field 引擎 | 固定 Field 实体、确定性应用 | 单目标、确定性执行、无自主演化 | 从 Feature(F) 层启动，激活关系层、能力层，调度内外资源，在约束层规则下完成固定流程执行 |
| Ego 引擎 | Ego 自演化实体 | 多目标、动态适配、自主迭代优化 | 从 Goal(G) 目标层启动，结合算法模型与外部反馈，动态调整实体内部结构与协作逻辑 |

核心定位总结：引擎是维持系统运行秩序的「执行管家」，并非决策大脑，所有执行行为必须服从约束层边界与目标层方向。

### 2.3.2 引擎内置能力

1. 全局 `表名+ID` 跨表解析器
2. Tick 窗口切换、状态归档、事务一致性保障
3. Q 构件调度求值、递归深度拦截，禁止无限递归 Q 调用
4. 双字典增删改查、版本同步；所有增删改操作封装引擎接口，上层禁止直接操作双字典；依靠 Key 前缀匹配定位节点，规避递归遍历

## 2.4 外部组件接入规范

所有外部程序、第三方框架、外部应用均可无缝接入 SurvX 体系，支持**轻量化接入 → 全能力演进**的渐进式适配方案。

**基础接入（轻量化）**

将外部组件直接封装为标准化 Q 能力单元，无需改造原有逻辑，即可参与系统数据流协作、能力调度。

**进阶演进（全能力）**

基于 Q 单元逐步补充结构、能力、关系、约束、目标等分层结构，迭代为完整 Matter 实体，获得状态管理、约束管控、数据驱动、自主演化的全量能力。

## 2.5 校验规则

### 2.5.1 引擎侧强制校验规则

以下规则为引擎层强制校验，任何实体、参数、Q 构件入库前必须通过。

**一、禁止孤立节点**

新增实体、参数、Q 构件，必须绑定作用域、关联、约束。校验不通过，拒绝入库。

**二、先定义后引用**

实体、参数 ID 必须预先注册，方可被引用。

**三、逻辑层禁止裸字符串**

逻辑层禁止裸字符串定位实体。L 符号层除外。所有运算引用，必须使用已注册 ID。

**四、允许双向因果 Q 闭环，禁止无限递归**

允许双向因果 Q 闭环。禁止无限递归 Q 调用，引擎自动拦截。

### 2.5.2 开发规范与架构约束

本章节为项目核心强制开发规则，用于统一迭代标准、防止架构跑偏、保障范式自洽。所有源码开发、功能迭代、组件接入必须严格遵守。

**强约束**

**一、能力必须抽象为 Q 单元**

所有系统能力必须抽象为标准化 Q 单元。禁止裸写独立业务流程，禁止碎片化逻辑。

**二、状态必须归属 Matter 实体**

所有运行状态、配置状态必须归属 Matter 实体管理。禁止定义游离全局变量、无归属状态。

**三、行为必须由 Energy 数据变动驱动**

所有业务行为、实体动作必须由 Energy 数据变动驱动。禁止编写主动轮询、主动触发逻辑。

**四、AI 仅可操作 Matter 结构化蓝图**

AI 仅允许生成、修改 Matter 结构化蓝图。禁止篡改执行流、绕过约束层、获取系统调度权限。

**五、Ego 演化必须由 Goal 驱动**

Ego 自我演化逻辑必须基于 Goal 目标层驱动。禁止硬编码固定演化规则、定向迭代逻辑。

**实现约定**

- **组件复用策略**：只读引用；修改则深度拷贝生成独立副本。
- **蓝图编译映射**：蓝图编译最终映射到 `_parameter / _constraint / _relation`。
- **简易脚本模式边界**：简易脚本可读取正式实例；回写只能局部合并，不维护完整持久化体系。
- **数据写入模式**：单条追加，不一次性批量写入大字典；支持增量动态更新。

## 3.2 register

命令：`python register.py reg <命令名> [目录] <脚本名>`

示例：

- 浮动最新：`python register.py reg cplugin CreatePlugin`
- 指定目录：`python register.py reg cplugin src CreatePlugin`
- 锁定版本：`python register.py reg cplugin CreatePlugin_20260921101000`
- 执行：`python register.py run <命令名> <参数...>`
- 示例：`python register.py run cplugin src FinDataFetcher`

作用：把命令名映射到脚本或指定版本脚本，作为统一入口转发执行，不动系统环境。

输入：命令名、可选目录、脚本名。

输出：写入 SQLite 映射表 `_register`，并可按注册命令转发执行。

存储：`.registry.db`，表 `_register`，字段 `key / value / version`。

规则：

- 注册时必须给脚本名，版本可选
- 不带版本：执行时在该目录下取该脚本最新版本
- 带版本：执行时固定使用该版本，找不到则报错
- 只在注册时记录的目录内查找，不跨目录扩大搜索
- 同一个命令名重复注册时覆盖原记录，不追加历史

状态：讨论中。

备注：对应 SurvX 注册表机制，命令入口稳定，版本可切换。

## 3.3 createPlugin

命令：`python CreatePlugin.py [目录] <实体名>`

示例：

- 默认当前目录：`python CreatePlugin.py FinDataFetcher`
- 指定目录：`python CreatePlugin.py src FinDataFetcher`

## 3.4 plugin

命令：`python <实体名>_<版本>.py`

示例：`python FinDataFetcher_20260921111003.py`

作用：承载一个 hoc 实例的结构蓝图、初始数值、Q 函数与启动逻辑。

输入：无（脚本自身即实例）。

输出：由 `f_main` 指向的 Q 函数决定；当前为占位，无实际输出。

存储：单文件 Python 脚本，hoc 临时脚本态。

结构：

- 第 1 段：结构蓝图（Matter），平铺路径 key，S / C / R / O / F 按需声明

- 第 4 段：内存表 / 注册表，`_state`、`_register` 单列，不进实例字典
- 第 5 段：启动块，从 `<实体名>_f_main` 取 Q 名，找函数并调用

规则：

- 顶层字典名 = 实体名，路径 key 平铺
- 不声明空结构，需要时再写
- S / C / R / O / F 按需声明，写了哪层哪层不能空
- `f_main` 指向主入口 Q
- 启动块放在末尾，保证所有定义已完成
- 文件越写越长是 hoc 常态，稳定后迁 dbfs

## 3.5 publish

命令：`python publish.py reg <命令名> <源目录> <目标目录>`

示例：

- 注册：`python publish.py reg pubw models works`
- 注册：`python publish.py reg pubi works instances`
- 发布：`python publish.py pubw tools/xx/yy.py`

作用：把命令名映射到一组“源目录 → 目标目录”，按映射把单个脚本从源目录发布到目标目录，只做文件复制。

输入：命令名、源目录、目标目录；发布时输入命令名、脚本子路径。

输出：写入 SQLite 映射表 `_publish`，并可按注册命令发布单个脚本。

存储：`.registry.db`，表 `_publish`，字段 `key / source / target`。

规则：

- 注册时必须给命令名、源目录、目标目录
- 发布时只给命令名和脚本子路径，子路径原样拼到源和目标后面
- 一个目标目录只允许对应一个源目录
- 重复注册同一目标目录时，提示是否覆盖，覆盖则更新原记录
- 只支持单文件发布，不支持目录同步
- 源路径不存在、源路径是目录、是数据库文件，均报错中止
- 同名文件直接覆盖
- 只做正向发布，不反向回流

状态：讨论中。

备注：对应 SurvX 发布机制，逐脚本放行；正式版可在此基础上加合规检查。

## 3.6 CreateApp

命令：`python CreateApp.py [目录] <app名>`

示例：

- 默认当前目录：`python CreateApp.py myapp`
- 指定目录：`python CreateApp.py src myapp`

作用：根据目录与 app 名生成 dbfs 应用实例，包含 SQLite 结构库、DuckDB 能量库、Q 目录与启动器。

输入：可选目录、app 名。

输出：生成 `<目录>/<app名>/` 完整骨架。

存储：

- `<app名>.db`：SQLite，Matter 结构，表名 `<app名>`
- `_forge.db`：SQLite，质量控制表 `_forge`
- `_<app名>.duckdb`：DuckDB，Energy 所有表
- `q/`：Q 文件目录
- `<app名>.py`：启动器

产物：

```
<目录>/<app名>/
├── <app名>.db          # SQLite，Matter 结构，表名 <app名>
├── _forge.db           # SQLite，质量控制表 _forge
├── _<app名>.duckdb     # DuckDB，Energy 所有表
├── <app名>.py          # 启动器
└── q/
    └── qxxxxxx.py      # 主入口 Q
```

规则：

- app 名即目录名，先创建 `<目录>/<app名>/`
- `<app名>.db` 只放本体结构：Matter 表，插入一条 `<app名>_f_main` 指向主入口 Q
- `_forge.db` 单独文件，放质量控制表 `_forge`
- `_<app名>.duckdb` 放所有 Energy 表：`_parameter`、`_constraint`、`_relation`、`_sequence`、`_experience`、`_intent`、`_feedback`、`_language`、`_train`、`_report`、`_llm`、`_register`
- `_register` 不加 version，随时改随时 update
- Q 名随机生成，格式 `q` + 随机数，暂不查重
- Q 文件头部版本、时间使用生成时的北京时间
- Q 函数体先 `print("hello world")` 再 `return`
- 启动器从 Matter 表取 `<app名>_f_main`，动态 import 对应 Q 并调用
- 入口文件名为 `<app名>.py`，跟 app 名一致

状态：讨论中。

备注：对应 SurvX dbfs 实例初始化机制；后续可在此基础上加合规检查、版本行、分表机制。
