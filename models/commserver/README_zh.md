# commserver

SurvX 实例的通讯层。对内、对外统一用 HTTP 与 WebSocket。

## 需求

一个应用总要有通讯。内部模块之间要通，外部系统也要通。

模块内直接调用当然就是 import，不需要走服务。但有两种场景需要独立通讯层：

- 内部按微服务结构拆，各起各的端口，进程之间要通
- 进程之间要加队列、要广播、要订阅

SurvX 里 Matter 又是运行时可变的：结构会新增、参数会更新、Q 会有版本、Ego 会自主调整、外部组件会陆续接入。

所以通讯层不能写死，也不能搞两套。它必须做到：

- 运行时能加、能改、能删接口，不重启
- 能广播数据变动
- 进程之间能互相调用、互相订阅
- 新版本能力上线时，不靠重启切换

一句话：**一套通讯层，进程内 import 之外的那部分，内外都用它，且跟着 Matter 演化。**

## 设计

- **HTTP 动态路由**：一个名字 = 一个模块 = 一个函数 = 一个路径。启动从 `routes.json` 加载，运行时支持注册、热重载、注销。对外接口、跨进程调用，走的是同一套。
- **WS 广播频道**：一个名字 = 一个 `/ws/{name}` 频道，连上的人互相广播，频道之间隔离。对外推送、进程间订阅，走的是同一套。
- **广播模型**：每连接一个发送队列 + 发送协程，广播时只入队不等待网络。慢客户端丢消息，不拖累别人。

对应范式：它实现的是 **Field.R（关系层）**——既承载实例与外部世界的关系，也承载进程之间的关系。业务能力以函数形式挂载，不裸写流程。

## 技术

- **FastAPI**：承载 HTTP 与 WebSocket
- **uvicorn**：运行服务，可选 uvloop 提速
- **内存字典**：管理路由表与频道池，hoc 态无持久化需求
- **管理接口无鉴权**：原型阶段取舍，生产需自行加

## 定位

理念验证原型，非生产可用。后续可收编为引擎内置能力，届时注册表归 Matter.R，由 Energy 驱动。
