# 前端引擎化设计方法文档

## 一、核心理念

### 1.1 一句话总结

**前端无脑，后端发指令；HTML极简，字典管一切。**

### 1.2 设计哲学

| 原则 | 说明 |
|---|---|
| 前端无逻辑 | 前端只负责创建元素、绑定事件、执行指令，不做业务判断 |
| 后端控全局 | 所有业务逻辑在后端，后端通过指令控制前端行为 |
| 字典是索引 | 前端维护 uid → 元素的映射，值存在 DOM 里 |
| 有值必有键 | 页面上任何一个值，都必须对应一个可追溯的 uid |
| 标签驱动 | 通过标签批量查询、批量绑定行为，不用 class |
| 内容优先 | 界面极简，没有隐藏菜单，内容平铺展示 |
| 数据驱动布局 | 每个块有 min/ideal/max，引擎自动计算位置和尺寸 |

## 二、文件结构

最简结构（四个文件）：

```
project/
├── server.py       # FastAPI 后端，负责所有业务逻辑
├── index.html      # 页面壳，只负责加载 JS
├── engine.js       # 引擎，通用底层能力
└── main.js         # 业务配置，调用引擎
```

### 各文件职责

| 文件 | 职责 |
|---|---|
| `index.html` | 只有一个空 body，加载 engine.js 和 main.js |
| `engine.js` | 字典管理、元素创建、读写、事件、指令执行 |
| `main.js` | 创建页面结构、绑定事件、调用引擎 API |
| `server.py` | 接收事件、生成指令、返回给前端 |

## 三、HTML 规范

### 3.1 页面壳

```html
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>main</title>
</head>
<body>
    <script src="/static/engine.js"></script>
    <script src="/static/main.js"></script>
</body>
</html>
```

**只有这些，没有其他。**

### 3.2 DOM 结构规范

- **全部用 `<div>`**：布局、容器、文本展示，一律用 div
- **表单元素例外**：`input`、`select`、`textarea` 保留（浏览器原生功能不可替代）
- **不用 class**：一个 class 都不写
- **不用语义标签**：不用 `header`、`nav`、`article` 等
- **每个元素带 `data-uid`**：唯一标识

### 3.3 DOM 示例

```
body
  └── div (data-uid="app")
        ├── div (data-uid="title")
        ├── div (data-uid="form")
        │     ├── input (data-uid="input1")
        │     └── button (data-uid="btn1")
        └── div (data-uid="echo")
```

### 3.4 为什么不用语义标签

因为是内部应用 / 本地应用：

- 不需要 SEO
- 不需要无障碍访问
- 语义不来自标签名，来自字典里的标签

## 四、字典设计

### 4.1 结构（轻量版）

```javascript
Dict = {
  "el1": {
    tags: ["待办", "可点击"],   // 标签列表
    element: <DOM元素>          // 元素引用
  },
  "el2": {
    tags: ["待办", "可删除"],
    element: <DOM元素>
  }
}
```

### 4.2 设计决策：值不在字典里

| 方案 | 值存哪 | 特点 |
|---|---|---|
| 方案一 | 字典里 | 数据集中，但需要同步 |
| **方案二（选用）** | **DOM 里** | **天然一致，字典轻量** |
| 方案三 | 混合 | 复杂，不推荐 |

**选用方案二的理由：**

- 值和 DOM 天然一致，不会出现字典和页面不一致的问题
- 字典只管分类和定位，职责单一
- 读写统一走引擎接口，业务代码不碰 DOM

### 4.3 字典的字段

| 字段 | 说明 |
|---|---|
| `tags` | 标签列表，用于分类和批量操作 |
| `element` | 指向真实 DOM 元素 |

## 五、引擎（Engine）设计

### 5.1 职责

引擎是通用底层能力，不包含任何业务逻辑。

### 5.2 方法清单

| 类别 | 方法 | 作用 |
|---|---|---|
| **字典** | `dict` | 存储所有条目 |
| **UID** | `uid.next()` | 生成唯一 id |
| **创建** | `createElement(tag, parent, options)` | 创建元素并注册到字典 |
| **获取** | `getElement(uid)` | 根据 uid 拿 DOM 元素 |
| **标签** | `setTags` / `addTag` / `removeTag` | 标签操作 |
| **查询** | `findByTag` / `findByTags` / `findByValue` | 批量查找 |
| **读取** | `read(uid)` | 从元素读取值 |
| **写入** | `write(uid, value)` | 把值写到元素 |
| **删除** | `removeElement(uid)` / `clearAll()` | 移除元素 |
| **事件** | `on(tag, event, handler)` | 按标签批量绑定 |
| **通信** | `sendEvent(event, uid, value)` | 发送事件到后端 |
| **执行** | `execute(instructions)` | 执行后端返回的指令 |
| **启动** | `start(config)` | 启动引擎 |
| **调试** | `lookup` / `inspect` / `allTags` | 调试工具 |

### 5.3 读写规则

**读（read）：**

| 元素类型 | 读出的值 |
|---|---|
| div / span | textContent（字符串） |
| input[type=text] | value（字符串） |
| input[type=number] | Number 或 null |
| input[type=checkbox] | checked（布尔） |
| select / textarea | value（字符串） |

**写（write）：**

- 根据元素类型自动判断写入方式
- 写值 = 只改 DOM（字典不存值）

### 5.4 指令执行

引擎是**指令执行器**。后端返回指令列表，引擎逐条执行。

支持的指令：

| 指令 | 作用 |
|---|---|
| `write` | 把值写到某个 uid |
| `setTag` | 给元素加标签 |
| `removeTag` | 移除标签 |
| `create` | 创建新元素（预留） |
| `remove` | 删除元素（预留） |
| `animate` | 播放动画（预留） |

## 六、后端设计（FastAPI）

### 6.1 核心接口

只有一个接口：

```
POST /api/event
```

接收前端事件，返回指令列表。

### 6.2 数据模型

```python
class Event(BaseModel):
    event: str      # 事件类型：click、input、change...
    uid: str        # 触发事件的元素 uid
    value: str = "" # 事件携带的值
```

### 6.3 返回格式

```json
{
  "instructions": [
    { "action": "write", "uid": "title", "value": "你点击了按钮" },
    { "action": "setTag", "uid": "btn1", "tag": "disabled" }
  ]
}
```

### 6.4 职责分工

| 层 | 职责 |
|---|---|
| 前端 | 发送事件、执行指令 |
| 后端 | 接收事件、生成指令 |

**所有业务逻辑都在后端。**

---

## 七、通信流程

### 7.1 完整流程

```
1. 用户操作（点击、输入）
2. 前端发送事件到后端：{ event, uid, value }
3. 后端处理，生成指令列表
4. 前端接收指令，逐条执行
5. 用户看到界面变化
```

### 7.2 前端全程不知道"为什么"

- 前端只知道"做什么"（执行指令）
- 不知道"为什么做"（业务逻辑在后端）

### 7.3 示例

用户点击按钮：

```
前端 → 后端：{ event: "click", uid: "btn1" }
后端 → 前端：{
  instructions: [
    { action: "write", uid: "title", value: "你点击了按钮" },
    { action: "write", uid: "btn1", value: "已点击" }
  ]
}
前端执行：标题变了，按钮文字变了
```

## 八、布局设计

### 8.1 核心思路：弹性拼图布局

每个块有尺寸约束：

| 属性 | 说明 |
|---|---|
| `ideal` | 最舒服的尺寸 |
| `min` | 最小能缩到多少（可以是 0，即消失） |
| `max` | 最大能撑到多少 |

### 8.2 布局规则

1. 所有块平铺，**没有层级**
2. 按每个块的 ideal 分配空间
3. 页面空间变化时，按比例缩放所有块
4. 缩放受 min/max 约束

### 8.3 聚焦行为

当某个块被"用到"（点击、聚焦）时：

- 它放大到最大舒适尺寸
- 其他块自动缩小让位
- 变化过程由透明层做动画

### 8.4 类比

- 每个块 = 一件家具
- 页面 = 一个房间
- 布局 = 在不违反家具本身性质的前提下，合理摆放

## 九、CSS 规范

### 9.1 原则

- **CSS 代码量最小化**：布局由引擎算，不由 CSS 写
- **只用 flex + grid**：所有布局用这两套工具
- **样式即材质**：CSS 只管视觉（颜色、字体、圆角、阴影），不管骨架
- **无 class**：样式通过 `[data-uid="..."]` 驱动

### 9.2 与布局分离

| 层 | 负责 |
|---|---|
| 引擎 | 位置、尺寸、层级 |
| CSS | 颜色、字体、边框、阴影 |

### 9.3 简化效果

传统 CSS 500 行 → 引擎方案 200 行以内。

## 十、动画设计

### 10.1 分层

| 层 | 职责 |
|---|---|
| 底层（平铺层） | 展示内容，只有缩放变化 |
| 上层（透明层） | 专门做动画，动画结束消失 |

### 10.2 好处

- 底层稳定，不因动画闪烁或重排
- 动画自由，想做什么都行
- 两层互不干扰
- 性能好（都用 GPU 加速）

### 10.3 实现

透明层是一个 `position: fixed` 的全屏 div，`pointer-events: none`，所有动画画在上面。

## 十一、设计原则总结

| 原则 | 说明 |
|---|---|
| 前端无逻辑 | 所有业务判断在后端 |
| 后端发指令 | 后端返回指令列表，前端执行 |
| 值在 DOM | 字典不存值，只存标签和元素引用 |
| 有值必有键 | 每个值对应一个 uid |
| 标签驱动 | 批量操作通过标签，不用 class |
| 全用 div | 布局容器一律用 div |
| 平铺无层级 | 所有块平等，没有嵌套 |
| 尺寸约束 | 每个块有 min/ideal/max |
| 弹性缩放 | 引擎按比例自动计算 |
| 动画分层 | 底层平铺，上层动画 |
| CSS 最小化 | 只管视觉，不管布局 |
| AI 友好 | 字典是结构化数据，AI 可直接操作 |

---

## 十二、这套设计的适用场景

### 适合

- 内部管理系统
- 本地应用
- 局域网应用
- 以内容展示为主的界面
- 需要 AI 辅助操作的场景

### 不适合

- 对 SEO 有要求的公网页面
- 需要无障碍访问的场景
- 对性能极致敏感的页面（大量 DOM 操作）
- 需要离线运行的纯静态页面

## 十三、与现有方案的对比

| 维度 | 传统前端 | 本方案 |
|---|---|---|
| HTML | 有 class、语义标签、事件属性 | 只有 div + data-uid |
| CSS | 按页面划分，容易冲突 | 按 uid 驱动，无冲突 |
| 逻辑 | 前端处理业务 | 后端发指令，前端执行 |
| 状态 | 散落在各处 | 值在 DOM，分类在字典 |
| 数据流 | 双向、复杂 | 单向：事件 → 后端 → 指令 → 执行 |
| AI 友好 | 需要理解代码 | 直接操作字典 |
| 调试 | 断点追踪 | 查字典 |

---

## 十四、一句话总结

**这是一套"字典驱动、标签分类、调度器协调、HTML极简"的前端体系。它的本质是：让 HTML 回归容器本质，让字典承载所有意义，让后端承载所有逻辑。**
